# UlmGap, plan 13 : suivi de cuve et carburant « bidon perso »

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** suivre les litres de la cuve (remplissages, avitaillements à la
clôture, pleins hors vol, relevés de jauge) et créditer le pilote qui
apporte son propre carburant (spec §13).

**Architecture :** même modèle que la caisse (plan 11) : document d'état
`tank/main` + historique non modifiable `tankMovements`, écrits ensemble
dans chaque transaction (`postTankMovement`, sur le modèle de
`postCashMovement`). La clôture reçoit la provenance du carburant ajouté
(`fuelFromTank`, `fuelFromPersonal`, `fuelSupplierUid`) et écrit, dans sa
transaction, le mouvement de cuve et le crédit `fuel_supply`. La
correction et la suppression admin régularisent les deux, sur le modèle du
crédit d'instruction (`instructionAdjustments`).

**Tech Stack :** inchangée.

**Spec :** `docs/superpowers/specs/2026-09-25-ulmgap-app-design.md`, §13
(révision du 2026-10-15), plus §9, §11, §4.5.

**Branche :** `feature/cuve` (déjà créée depuis `main`).

## Global Constraints

- Toujours `fvm flutter` / `fvm dart`. TDD (preuves RED puis GREEN). Textes
  en français. Jamais de déploiement en prod.
- Règle absolue : `tank/main.liters` n'est jamais modifié sans sa ligne
  `tankMovements`, dans la même transaction ; idem caisse
  (`postCashMovement`) et comptes (`postMovement`). Toutes les lectures
  d'une transaction Firestore avant toute écriture.
- `tankMovements.kind` ∈ `refill` / `flight` / `aircraft_fill` / `gauge` /
  `flight_adjustment` ; `liters` entier signé (positif = entrée) ; `date`
  « AAAA-MM-JJ » (jour du club ; jour du vol pour un vol) ; champs
  `flightId`, `aircraftId`, `cashMovementId`, `measuredLiters`,
  `technical`, `note`, `by`, `at`, `litersAfter` (voir spec §13.1).
- Niveau de cuve : peut être négatif, jamais bloquant ; affiché en orange
  s'il est négatif.
- Clôture : `fuelFromTank` et `fuelFromPersonal` entiers ≥ 0, somme ≤ 100 ;
  `fuelSupplierUid` obligatoire si `fuelFromPersonal` > 0 et membre de
  `crew`, sinon `null` ; `fuelAdded` n'est plus envoyé : le serveur le
  calcule (somme). Messages :
  - « Carburant ajouté : 100 L au maximum au total. » ;
  - « Choisissez le pilote qui a fourni le carburant. » ;
  - « Le pilote qui a fourni le carburant doit faire partie de l'équipage. ».
- Crédit bidon perso : `round(fuelFromPersonal × fuelLiterPrice)`,
  transaction **`fuel_supply`**, motif « Carburant fourni (bidon perso) »
  (régularisation : « Régularisation carburant fourni »), `flightId` du vol,
  notification habituelle d'un mouvement. Ni caisse ni cuve.
- Tarif `fuelLiterPrice` (« Prix du litre (bidon perso) »), défaut 600,
  0 à 10 000, lu au moment de la clôture dans les tarifs courants.
- Libellés : choix « Aucun » / « Depuis la cuve » / « Bidon perso » /
  « Les deux » ; champs « Litres pris à la cuve », « Litres du bidon
  perso », « Pilote ayant fourni le carburant » ; « Crédit : 20 L × 600 =
  12 000 FCFA pour XXX » ; historique « Carburant fourni (bidon perso) » ;
  libellés de cuve « Remplissage », « Vol », « Plein hors vol », « Relevé
  de jauge », « Régularisation » ; écran « Suivi cuve » ; ligne « Cuve :
  180 L » ; champ « Litres (facultatif) » de l'Achat carburant ; boutons
  « Plein d'un appareil », « Relevé de jauge ».
- Droits : opérations de cuve (plein hors vol, relevé) : instructeurs et
  admins. Lecture `tank` et `tankMovements` : instructeurs et admins.
- `formatFcfa` émet U+00A0 avant « FCFA » et U+2212 pour un négatif.
- Tests : `fvm flutter test && fvm flutter analyze` ; `cd functions && npm
  test` ; intégration `cd functions && JAVA_HOME=/opt/android-studio/jbr
  PATH=/opt/android-studio/jbr/bin:$PATH npm run test:int` (juger sur
  `# fail` / `not ok`). Tout fichier d'intégration qui touche la cuve ou la
  caisse appelle `resetTank` / `resetCashbox` en `beforeEach` **et**
  `afterEach`.

## Review Focus

- **Clôture « Les deux » :** une seule transaction écrit le vol, le
  mouvement de cuve (−litres cuve) et le crédit du pilote ; le total
  `fuelAddedLiters` = somme. → test Task 3.
- **Correction admin qui change de pilote fournisseur et de litres :**
  retrait chez l'ancien, ajout chez le nouveau, écart de cuve exact. → test
  Task 3.
- **Suppression admin d'un vol clôturé avec carburant cuve et bidon :**
  litres remis en cuve, crédit retiré. → test Task 3.
- **Plein hors vol puis clôture tardive d'un vol plus ancien :** le
  carburant actuel de l'appareil n'est pas écrasé. → test Task 3.
- **Vol clôturé avant le plan 13 corrigé par un admin sans provenance :**
  aucun mouvement de cuve ni crédit créé. → test Task 3.
